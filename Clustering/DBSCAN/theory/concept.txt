What is DBSCAN?
-----------------------------------------------------------------------------------------------------------------------------------------------------------------------
DBSCAN stands for Density-Based Spatial Clustering of Applications with Noise. The core idea is dead simple: a cluster is a dense region of points, separated from other dense regions by sparse space.
It doesn't ask "how far are you from a centroid?" It asks "how many neighbors do you have within radius ε?" If enough — you're part of a cluster. If none — you're noise.

Two parameters control everything: ε (epsilon) defines the neighborhood radius, and MinPts defines how many points make a neighborhood dense.

Properties:
-----------------------------------------------------------------------------------------------------------------------------------------------------------------------
1. Clusters are dense regions separated by sparse space.

2. Clusters have arbitrary shapes (not limited to spheres).
    Arbitrary shapes. KMeans clusters are always convex blobs because they're built around centroids. 
    DBSCAN follows density chains — it can find rings, crescents, interleaved S-curves, any shape where points are locally dense. 
    This is why it dominates in geo-clustering, where clusters are cities or neighborhoods with irregular shapes.

3. DBSCAN can identify outliers (noise) naturally.
    Points that don't belong to any dense region aren't forced into the nearest cluster — they get labeled -1 (noise). 
    This is DBSCAN's biggest practical advantage over KMeans for anomaly detection. 
    KMeans silently absorbs every outlier into whatever cluster is nearest; you have no idea they're outliers.

4. It does not require specifying the number of clusters beforehand.
   You never specify the number of clusters. The algorithm discovers them by following density. 
   This is a massive practical advantage — in real-world data you often don't know K, and guessing wrong with KMeans gives you garbage.

How it fundamentally differs from KMeans
-----------------------------------------------------------------------------------------------------------------------------------------------------------------------
KMeans is a partition algorithm — every point must belong to exactly one cluster, clusters are defined by centroids, and the goal is to minimize within-cluster sum of squares (WCSS). It's optimization-based.
DBSCAN is a density traversal algorithm — it has no objective function, no centroids, no convergence criterion. It just asks: "are these points dense enough together to be called a cluster?" It's rule-based.
This also changes how you evaluate them. WCSS is meaningless for DBSCAN (there are no centroids to measure distance from). Instead you use silhouette score or DBCV.
One more critical difference: KMeans has an initialization problem — random centroid placement can land in bad local minima, so you run it multiple times (KMeans++). DBSCAN has no initialization at all. It's mostly deterministic

ε (epsilon) is a distance. It draws a circle around every point. Everything inside that circle is that point's neighborhood. The circle size is the same for every point in the dataset.
MinPts is a count. It says: "how many neighbors must be inside your ε-circle for you to be considered a dense point?" If you have ≥ MinPts neighbors, you're dense. If not, you're sparse.

These two numbers together define what "dense" means for your dataset.
Now, once you can classify every point as dense or sparse, DBSCAN assigns each point one of three types.

Important Definitions:
-----------------------------------------------------------------------------------------------------------------------------------------------------------------------
Core Point:
Core point — has ≥ MinPts neighbors within ε. This point lives in a dense region. 
It is the engine of DBSCAN: cluster expansion always starts from a core point and propagates outward through other core points. 
Think of them as the "interior" of a cluster

Border Point:
has fewer than MinPts neighbors within ε, so it is not dense by itself. 
But it falls within the ε-circle of at least one core point. 
It gets pulled into that cluster as a passenger, not a driver. 
It can never start or expand a cluster.

Noise Point (Outlier):
A noise point is neither a core point nor a border point. 
It has fewer than MinPts neighbors, and none of those neighbors are core points. 
Noise points are isolated points in sparse regions. 
DBSCAN doesn't force them into any cluster — they remain unlabeled (or labeled as -1), clearly separated from the dense regions.    


"can a border point be noise?" — 
the answer is no, by definition. Once a point is within ε of any core point, it is at minimum a border point. 
"can a border point belong to two clusters?"
Yes — this is the border point ambiguity. If a border point sits within ε of two different core points from two different clusters, which cluster it joins depends on traversal order. 
This is the one non-deterministic behavior in DBSCAN

DBSCAN Algorithm Steps:
-----------------------------------------------------------------------------------------------------------------------------------------------------------------------
for each unvisited point P:
    mark P as visited
    neighbors = regionQuery(P, ε)

    if len(neighbors) < MinPts:
        label P as NOISE            # tentative — can change!
    else:
        C = new cluster
        expandCluster(P, neighbors, C)

expandCluster(P, neighbors, C):
    add P to C
    queue = neighbors
    while queue not empty:
        Q = queue.pop()
        if Q is NOISE: reassign Q to C   # border point rescue
        if Q is unvisited:
            mark Q as visited
            Q_neighbors = regionQuery(Q, ε)
            if len(Q_neighbors) >= MinPts:
                queue += Q_neighbors     # Q is core — keep expanding
        if Q not yet in any cluster:
            add Q to C


How DBSCAN Works (The Intuitive Explanation)
-----------------------------------------------------------------------------------------------------------------------------------------------------------------------
Imagine you're walking through a city at night, and you want to group neighborhoods together.

1. Pick a random person (point).
2. Look around you in a circle of radius ε (epsilon).
3. Count how many people are in that circle (including yourself).
4. If you have 5 or more people (MinPts), you're a "core" person — you're in a dense area.
5. If you have fewer than 5, you're "sparse" for now.
6. If you're sparse, you might be noise, OR you might be close enough to a core person to be their "border" friend.
7. If you're a core person, you start a new neighborhood (cluster).
8. Then you look at all your core friends and their friends, and you keep expanding the neighborhood as long as you keep finding more core people.
9. You stop when you can't expand anymore.
10. Then you go back to step 1 and pick another unvisited person.

That's exactly what DBSCAN does — it finds dense regions and expands them until they can't grow anymore, leaving sparse points as noise.

Noise is tentative. A point marked noise early on can be rescued later. 
If it gets added to the expansion queue of a core point discovered afterward, it gets reassigned to that cluster. 
This is why noise = "no core point found this person yet" rather than "permanently isolated."

BFS vs DFS doesn't affect the final clusters. 
Using a queue (BFS) or a stack (DFS) for expansion changes the order points are processed, but the final set of core and border points is identical. 
The one exception is border points that sit equidistant between two clusters — BFS and DFS can assign those differently. That's the non-determinism covered in topic 7.

The real cost is regionQuery. Every call to regionQuery(P, ε) has to find all points within distance ε of P. 
Naively that's O(N) per point — O(N²) total. 
This is where a KD-tree or ball-tree brings it down to O(log N) per query, making the whole algorithm O(N log N). 
This is the entire scaling story for DBSCAN.
