1. WHAT IS FEATURE IMPORTANCE?
--------------------------------------------------------------------------------
Feature importance tells you which input columns (features) the tree relied on
the most to make predictions.

In a decision tree, a feature becomes important when splitting on it makes the
data in the child nodes "cleaner":
- for classification: cleaner = more of a single class (lower impurity)
- for regression: cleaner = targets closer to each other (lower error/variance)

So: higher importance = the feature helped the tree make better splits.


2. DEFAULT TREE IMPORTANCE: MEAN DECREASE IN IMPURITY (MDI)
--------------------------------------------------------------------------------
This is the default `feature_importances_` one gets in scikit-learn trees and
random forests.

Idea:
Every time the tree uses a feature to split a node, we give that feature "credit"
equal to how much that split reduced impurity.

For a node t that splits using feature f:

ImpurityDecrease(t) =
    Impurity(parent t)
  - [ (N_left / N_t)  * Impurity(left child)
    + (N_right / N_t) * Impurity(right child) ]

Then accumulate for feature f, weighted by how many samples reached the node:

Importance(f) += (N_t / N_total) * ImpurityDecrease(t)

Where:
- N_total  = total training samples
- N_t      = samples reaching node t
- N_left, N_right = samples going to left/right child
- Impurity = Gini or Entropy (classification), MSE/MAE (regression)

Normalization:
After summing across all nodes, scale the importances so that:
sum_f Importance(f) = 1.0


3. HOW TO READ THE NUMBERS (INTUITION)
--------------------------------------------------------------------------------
- High importance:
  The feature is used in splits that reduce impurity a lot, often near the top
  of the tree (root/early nodes) where many samples pass through.

- Low importance:
  The feature is used rarely, or only deep in the tree where few samples reach.

- Zero importance:
  The feature was never used for any split (the tree ignored it).


4. PROS AND CONS OF MDI (WHAT CAN GO WRONG)
--------------------------------------------------------------------------------
Pros:
- Free + fast: computed during training, no extra evaluation needed.
- Works with non-linear patterns and interactions automatically.

Cons (important in real projects):
- High-cardinality bias:
  Features with many possible split points (continuous features or many-category
  columns like zip codes / IDs) can look artificially important.

- Overfitting / training-set bias:
  MDI is based on training splits. If the tree overfits, it can assign high
  importance to noisy patterns that won’t generalize.

- Correlated features:
  If two features carry the same information, the tree may pick only one early.
  That chosen one gets high importance, the other looks unimportant even though
  it’s actually useful.

- No direction:
  MDI tells you "this feature matters", but not whether higher values increase
  the prediction or decrease it (no + / - effect).


5. BETTER CHECK: PERMUTATION IMPORTANCE (MDA)
--------------------------------------------------------------------------------
Permutation importance answers a more direct question:
"If I destroy this feature, how much does model performance drop?"

Steps (use validation/test set):
1) Measure baseline metric (Accuracy/AUC/F1 for classification; RMSE/MAE for regression)
2) Shuffle one feature column (break its relationship with the target)
3) Recompute the metric
4) Importance = (baseline score - shuffled score)  (or increase in error)

Interpretation:
- Big performance drop => feature is truly important for predictions
- Small/no drop => feature is not very useful (or redundant)

Why it helps:
- Evaluated on validation/test set => reflects generalization better than MDI
- Less biased toward “many split points” than MDI

If shuffling a feature makes the model much worse on validation data, that feature was carrying useful predictive information.
Permutation Importance is not specific to decision trees. It’s a general, model-agnostic method you can use for almost any supervised model and many datasets.

Works with:

Decision Trees, Random Forests, XGBoost/LightGBM/CatBoost
Logistic Regression, Linear/ElasticNet models
SVMs (if you can compute predictions)
Neural networks
k-NN, Naive Bayes, etc.

Works for:

Classification and regression
Any metric you can evaluate on a validation/test set (AUC, F1, logloss, RMSE, MAE…)

Why it’s “model-agnostic”
It doesn’t look inside the model. It only needs:

a trained model
a dataset (usually validation/test)
a metric function
Then it measures: “How much does performance drop if I break feature X?”

When it can mislead (important caveats)

Permutation importance is general, but it has known issues:

Correlated / redundant features
If two features contain the same info, shuffling one may not hurt much because the model can still use the other.
Result: each feature looks less important than it really is. (Conditional permutation importance is one fix.)
Time series / leakage / grouped data
If you shuffle a feature across time or across users, you may break real-world structure.
Example: forecasting sales, shuffling “price” across dates is unrealistic. Use time-aware evaluation and sometimes grouped permutation.
Expensive for large models
You re-score the dataset once per feature (often multiple repeats), so it can be slow.


6. SUMMARY: WHICH ONE TO USE
--------------------------------------------------------------------------------
Method: MDI (Gini/Entropy importance)
- Best for: quick, built-in first look
- Main issues: biased by cardinality, affected by overfitting, misleading with correlation

Method: Permutation importance
- Best for: more trustworthy global ranking on a validation/test set
- Main issues: slower; correlation can hide importance

Method: SHAP (TreeSHAP)
- Best for: explaining individual predictions + direction (+/- effect)
- Main issues: more compute and extra tooling/learning curve


PRACTICAL TAKEAWAY
--------------------------------------------------------------------------------
Use MDI as a quick hint, not as final truth.
For any serious feature selection or reporting, compute permutation importance
on a validation/test set, and use SHAP when you need to explain “why” for a
specific prediction.


Note:

High-cardinality bias
----------------------------------------------------------------------------------------
Cardinality = how many different values a feature can take.

Examples:

"Age" (continuous): can take many values (23.1, 23.2, 23.3, ...) -> high cardinality
"ZipCode": thousands of possible codes -> high cardinality
"Gender": {Male, Female} -> low cardinality
"Weekend": {Yes, No} -> low cardinality

Why trees get biased toward high-cardinality features
When a tree tries to split a node, it searches for a split that reduces impurity the most.

For a continuous feature, it can try MANY thresholds: Age < 21.5, Age < 22.0, Age < 22.5, ... (lots of choices)
For a feature like ZipCode/ID, there are MANY ways to isolate small groups: ZipCode == 56001 vs others, ZipCode == 56002 vs others, etc.

More choices = higher chance that the tree finds a split that looks "great" on the training data, even if it's just luck/noise.
So these features often get picked early and get large MDI importance, even when they are not truly useful.

Why this is specifically a problem for MDI (impurity-based importance)
MDI importance is computed from the same training splits the tree chose. If the tree picked a high-cardinality feature because it had many chances to find a good split, MDI will reward it heavily.
So MDI can say: "ZipCode is the most important feature" even if zip code is mostly noise or just overfitting.

How to spot and fix it -- practical

Spot:
Extremely high importance for ID-like columns (customer_id, transaction_id)
High importance for columns with many unique categories
Tree performs well on training but worse on validation

Fix:
Drop ID columns from training
Group rare categories (reduce cardinality)
Use permutation importance on a validation set (more reliable)
Use regularization: max_depth, min_samples_leaf (reduces memorization)
Prefer CatBoost for categorical handling (often more robust than naive encodings)
