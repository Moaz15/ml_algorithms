7. FEATURE IMPORTANCE AND INTERPRETABILITY

7.1 Impurity-based importance (MDI) and why it is biased
--------------------------------------------------------

What it is, in one line

    Every time the tree splits on a feature, that feature earns credit equal to the impurity the
    split removed. MDI is each feature's total credit, scaled so all of them add up to 1.


HOW IT IS COMPUTED

    For one split at node t on feature f:

        impurity drop  =  Impurity(t)  -  [ (n_left / n_t)  * Impurity(left child)
                                          + (n_right / n_t) * Impurity(right child) ]

    Credit it to f, weighted by how much of the data reached that node:

        Importance(f)  +=  (n_t / n_total) * impurity drop

    Sum over every node that split on f, then normalise so the importances total 1.

    Two things fall straight out of that formula. A split near the root counts for far more than one
    near the bottom, because n_t is much larger. And a feature the tree never split on scores
    exactly zero - not 'unimportant', just unused.

    This is what scikit-learn's feature_importances_ gives you, and it is free: every number in it
    was already computed while the tree was being built.


MEASURING IT

    feature             distinct values      MDI
    twin_b                         3000    0.840
    twin_a                         3000    0.115
    noise_highcard                 3000    0.040
    noise_binary                      2    0.005

    Two things to notice. noise_highcard is pure noise, and it still collects 0.040 - about 8 times
    what noise_binary gets, even though both carry exactly zero information. And twin_a and twin_b
    are equally good by construction, yet MDI hands 7 times more credit to one of them.


WHY IT IS BIASED

    Training data  :  MDI is computed from the splits the tree actually made, on the data it was
                      fitted to. A split that only worked by luck still earns full credit, so an
                      overfit tree produces confident nonsense.

    Cardinality    :  a feature with more distinct values gets more candidate thresholds, so it wins
                      more splits and collects more credit. See 6.6.

    Correlation    :  when two features carry the same information the tree picks one, and that one
                      takes the credit for both. See 7.5.

    No direction   :  MDI says a feature mattered. It never says whether a higher value pushes the
                      prediction up or down.


> Real-world: MDI is fine as a first glance - it is already there and it costs nothing. It is not
  fine as the number you put in a slide, use to drop columns, or hand to a stakeholder as "what
  drives the model". For any of those, measure on held-out data instead.

> Likely follow-up: "A feature has zero MDI. Is it useless?"
  No - it means the tree never split on it, which is a different claim. A perfect duplicate of the
  root feature scores zero. So does a genuinely useful feature that lost every scan by a hair. Zero
  MDI tells you about the tree, not about the feature.


7.2 Permutation importance
--------------------------

What it is, in one line

    Shuffle one column so it still looks the same but no longer lines up with the target, then see
    how much the model's score falls. If the model needed that column, the score drops.


THE PROCEDURE

    1.  Score the fitted model on held-out data. That is the baseline.
    2.  Shuffle one feature's column, leaving every other column untouched.
    3.  Score again. The drop is that feature's importance.
    4.  Repeat a few times and average, because the shuffle is random.

    Two properties matter, and they are exactly the two MDI lacks. It is measured on held-out data,
    so luck on the training set earns nothing. And it measures the effect on predictions, not on the
    tree's structure - it never looks inside the model, which is why the same method works on any
    model at all.


MEASURING IT

    feature                 MDI   permutation    agree?
    twin_b                0.840         0.058        NO
    twin_a                0.115         0.372        NO
    noise_highcard        0.040         0.003        NO
    noise_binary          0.005         0.005        NO

    The two methods do not merely disagree on the margins - they swap the top two. MDI says twin_b
    carries the model; permutation says twin_a does. Neither is lying. The tree happened to split on
    twin_b at the root so MDI credited it, while at prediction time the model leans on twin_a. The
    real lesson is that the question 'which of these two matters' has no answer, which is 7.5.

    Both methods agree on the part that is unambiguous: the two noise columns are worth nothing, and
    permutation puts them at roughly zero rather than giving noise_highcard the credit MDI did.


WHAT IT COSTS, AND WHERE IT MISLEADS

    Cost                  :  no refitting, but you re-score the dataset once per feature per repeat.
                             On a wide dataset with a slow model that adds up.

    Correlated features   :  shuffling one of a pair does little, because the model falls back on
                             the other. Both look unimportant. See 7.5.

    Grouped or time data  :  shuffling across time or across users destroys structure that was real,
                             so the drop overstates the feature's value. Permute within groups or
                             use a time-aware split.

    Negative values       :  a small negative importance just means the shuffle happened to help.
                             Read it as zero, not as evidence the feature hurts.


> Real-world: this is the number to report. It answers the question people actually mean when they
  ask which features matter - "what would break if this column went away" - and it is measured on
  data the model has not seen.

> Likely follow-up: "Should you refit the model after shuffling?"
  No. Permutation importance asks what THIS fitted model relies on. Refitting answers a different
  question - whether the feature is needed at all - and for that you drop the column and retrain,
  which costs one full fit per feature.


7.3 TreeSHAP for per-prediction explanation
-------------------------------------------

What it is, in one line

    MDI and permutation describe the model as a whole. SHAP describes one prediction: how much
    each feature pushed THIS row away from the average prediction.


THE GUARANTEE

    SHAP values are additive. Start from the average prediction over the whole dataset, add each
    feature's contribution for this row, and you land exactly on this row's prediction. Nothing is
    left over and nothing is double counted - that is the property that makes the numbers defensible
    rather than merely suggestive.

    Illustrative - a loan model, showing how one applicant's score is assembled:

        average prediction over everyone      0.20
        low income                           +0.25
        3 recent missed payments             +0.18
        high credit utilisation              +0.06
        long account history                 -0.07
        ------------------------------------------
        this applicant                        0.62

    0.20 +0.25 + +0.18 + +0.06 + -0.07 = 0.62


WHY "TREE" SHAP

    The problem  :  computing exact SHAP values in general means considering every subset of
                    features, which is exponential and hopeless past a handful of columns.

    The fix      :  TreeSHAP exploits the tree structure to get the same exact answer in polynomial
                    time, by pushing subsets down the tree instead of enumerating them.

    So           :  for trees and tree ensembles, exact per-prediction attributions are cheap enough
                    to run on every row in production. That is not true for models in general.


WHAT YOU GET THAT THE OTHERS DO NOT

    Per row     :  an explanation for one prediction, not an average over the dataset. This is what
                   you need when a person asks why THEIR application was declined.

    Direction   :  contributions are signed. MDI and permutation both tell you a feature mattered
                   but never which way it pushed.

    Global too  :  average the absolute SHAP values across rows and you get a global ranking,
                   computed from predictions rather than from tree structure.


> Real-world: regulated lending and insurance often require a reason code per decision - not "income
  matters in general" but "income is why this application was declined". An averaged importance
  cannot answer that; a per-row attribution can.

> Likely follow-up: "If SHAP is exact and gives direction, why use anything else?"
  Cost and dependencies. MDI is free and already computed, permutation is a dozen lines and works
  on any model. SHAP needs the library, more compute, and more care in reading it - the
  contributions are relative to a baseline you chose, and swapping that baseline changes every
  number.


7.4 Reading a tree as a rule set, and where interpretability breaks down
-----------------------------------------------------------------------

What it is, in one line

    Every path from the root to a leaf is one rule, written in plain English. A tree is just a
    stack of those rules, and that is the whole reason anyone calls trees interpretable.

        IF income > 50k AND tenure > 2 years  THEN approve

    Each leaf gives you exactly one such rule, so a tree with eight leaves is eight rules and
    nothing more. You can print it, read it, hand it to someone who has never seen a model, and they
    can check it against their own judgement.


WHERE IT BREAKS DOWN

    Depth              :  the rule count doubles with every level, and each rule gets one clause
                          longer. A depth-12 tree is thousands of rules with twelve conditions each,
                          which is not something a person reads.

    Repeated features  :  the same feature reappears at different thresholds down a path, so a rule
                          reads 'income > 50k AND income <= 80k AND income > 60k'. True, but not
                          explanation.

    Instability        :  refit on slightly different data and the rules change, sometimes
                          completely. A story you cannot reproduce next month is not much of a
                          story. See 6.1.

     max_depth   rules at most    can a person hold it?
             2               4                      yes
             3               8                      yes
             5              32              with effort
             8             256                       no
            12           4,096                       no

    For scale, the unpruned tree measured in 7.1 has 92 leaves - 92 rules - on four features. Nobody
    is reading that.

    The honest position is that a SMALL tree is interpretable, not that trees are interpretable. If
    interpretability is the reason you chose a tree, then depth is not just a variance knob - it is
    the feature you are actually buying, and you should constrain it on purpose and accept the
    accuracy you lose.


> Real-world: this is the trade behind "we used a tree so the business can follow it". That claim
  holds at depth 3 or 4. At depth 15 you have a black box that merely looks legible, which is worse
  than an honest one because nobody thinks to ask.

> Likely follow-up: "How deep can a tree be and still be explainable?"
  Three to five levels is where people actually read it, which is eight to thirty-two rules. Past
  that you are explaining with SHAP or permutation importance anyway - and at that point the tree's
  structure has stopped being the reason you chose it.


7.5 Correlated features splitting the credit between them
---------------------------------------------------------

What happens, in one line

    When two features carry the same information, the tree only needs one of them. Whichever one
    it happens to pick takes the credit, and the other looks worthless - even though they are
    interchangeable.


THE SAME FEATURE, TWO OPPOSITE VERDICTS

    MDI over-credits it           :  the tree split on twin_b at the root, so the impurity drops
                                     were booked there. MDI reports 0.840 - almost the whole model.

    Permutation under-credits it  :  shuffle twin_b and the model barely notices, because twin_a
                                     still carries the information. Permutation reports 0.058 -
                                     practically disposable.

    Same feature, both wrong      :  one method says twin_b is the model, the other says it is
                                     noise. With perfect duplicates it gets worse still: permutation
                                     drives BOTH to near zero, because either one alone covers for
                                     the other.


MEASURING IT

    shuffled                            accuracy drop
    twin_a alone                                0.372
    twin_b alone                                0.058
    twin_a and twin_b together                  0.443   <- what the information is really worth

    Shuffling either twin on its own understates the case. Shuffle them together - destroying the
    information rather than one copy of it - and accuracy falls by 0.443, more than either number
    alone. That is what the information is actually worth to the model, and neither per-feature
    method reports it.


WHAT TO DO

    Group them               :  cluster features by correlation and permute each cluster together,
                                the way the table above does. Report importance per group, not per
                                column.

    Or drop one              :  if two columns are genuinely redundant, keeping both buys nothing
                                and costs you a clean explanation. Drop one before you train.

    Read rankings carefully  :  a low importance score never means 'this feature is useless'. It
                                means 'removing only this feature costs little', which is a much
                                weaker statement.


> Real-world: feature sets built by teams accumulate near-duplicates - total_spend_30d and
  avg_daily_spend_30d, price and log_price, age and birth_year. Each pair splits its own importance,
  so a genuinely important signal can be spread thin enough across three columns that none of them
  look like they matter, and someone drops all three.

> Likely follow-up: "So which twin is the important one?"
  The question has no answer, and recognising that is the point. They are interchangeable - the
  tree picked one by a margin thinner than noise. The answerable question is what the pair is
  worth together, which is what grouped permutation measures.
